# Haptic design — how information becomes vibration

Everything upstream of the belt produces *information*: which of four directions
a hazard came from, which of three danger classes the AI heard, and how confident
it was. The belt has two vibration motors. This document is the mapping between
the two, and it is implemented in [`laptop/haptic.py`](../laptop/haptic.py).

## The rule, in one sentence

> **Where** you feel it says **where the sound is**.
> **How many times** you feel it says **what the sound was**.
> **How hard** you feel it says **how sure the AI is**.

The three cues use three separate channels, so they never interfere. "Siren from
the left" and "horn from behind" are unambiguous without the wearer having to
compare them side by side.

## Direction → which motors, in what order

| iOS direction | LEFT motor | RIGHT motor | What it feels like |
|---|---|---|---|
| `left` | ■ | | one-sided, left |
| `right` | | ■ | one-sided, right |
| `front` | ■ | ■ *(together)* | symmetric, arrives all at once |
| `back` | ■ → | → ■ *(then)* | travels across the body, left to right |
| `unknown` | | | nothing is sent |

`front` and `back` are both "not to one side", so with two actuators they cannot
be separated by *position*. They are separated by *order* instead: `front`
arrives as one symmetric event, `back` sweeps across. A sensation moving away
from the direction the wearer faces is the natural reading of "that came from
behind you".

The two halves of a sweep run with **no gap** between them (`off_ms = 0`), so one
pulse is felt as a single burst in motion rather than as two separate taps. The
firmware host test `back_sweep_is_sequential` exists specifically to stop this
collapsing into "both motors at once", which would silently destroy the whole
front/back distinction.

`unknown` means the iOS bridge's own role/margin gate was not satisfied, so there
is nothing trustworthy to point at. The belt stays **silent** rather than
buzzing vaguely: a directionless alert teaches the wearer to ignore the belt,
which is worse than missing one event.

## Danger class → how many pulses

| Class | Pulses | Pulse length | Gap | Total | Feels like |
|---|---:|---:|---:|---:|---|
| `crash` | 1 | 500 ms | — | 500 ms | one bang |
| `horn` | 2 | 240 ms | 140 ms | 620 ms | beep-beep |
| `siren` | 3 | 260 ms | 150 ms | 1080 ms | wee-oo-wee |

Pulse count is the most robust haptic channel available. It survives a loose
belt, a thick jacket, and a wearer who is walking; waveform subtleties do not.
Counting to three is also something a wearer can do without training.

Any other label — `normal` and anything else `meit-ai` reports — produces no
vibration at all.

## Confidence → PWM duty

Each class has its own intensity range, ordered by urgency:

| Class | Duty at confidence ≤ 0.50 | Duty at confidence ≥ 0.90 |
|---|---:|---:|
| `crash` | 72 % | 100 % |
| `siren` | 62 % | 92 % |
| `horn` | 55 % | 85 % |

Confidence is mapped linearly between those two bounds. A low-confidence alert
**still fires** — suppressing a real hazard is the worse error — but it is felt
as less urgent. The floor is 0.50 rather than 0 because a small softmax rarely
reports below chance level, and stretching the range down there would waste most
of the usable duty on values that never occur.

`--intensity-scale` multiplies the result at runtime (0.1–2.0) so a demo can be
turned down for a quiet room or up through winter clothing without editing the
profile.

## Constraints the numbers come from

Two hard limits shaped every value above.

**Motor spin-up.** An ERM or coin vibration motor needs roughly 50–80 ms to
reach a perceptible amplitude, so a burst much shorter than that is felt as
*nothing at all* rather than as a short pulse. `MIN_STEP_ON_MS = 100` is enforced
on every emitted step, **including each half of a sweep** — which is why class
pulses are at least 200 ms: a sweep halves them.

**Packet budget.** A CMD v3 packet is an 8-byte header plus 2 bytes per step. Six
steps is exactly 20 bytes, the most an ATT Write Request carries on the default
23-byte MTU, so an alert never depends on MTU negotiation succeeding. A sweep
costs two steps per pulse, so the pulse count is capped at **three**. A `siren`
from `back` is the worst case and lands on exactly 20 bytes.

Both limits are checked by `ClassProfile.validate()`, so an edited profile that
violates them fails at load rather than at the demo.

## Tuning it

[`laptop/haptic_profile.json`](../laptop/haptic_profile.json) holds the same
values as the built-in default and can be edited without touching code:

```bash
python -m laptop.haptic_preview --profile laptop/haptic_profile.json
python -m laptop.ios_motor_bridge --profile laptop/haptic_profile.json
```

A unit test asserts the file and the Python default stay identical, so editing
one without the other is caught rather than silently ignored. Constraints
enforced at load:

- `pulses` ≤ 3, so a sweep still fits six steps
- `on_ms` a multiple of 20 ms, so a sweep halves onto the 10 ms wire grid
- `on_ms` ≥ 200 ms, so each sweep half clears the perceptibility floor
- `gap_ms` a multiple of 10 ms
- `1 ≤ min_intensity ≤ max_intensity ≤ 100`

## What a belt on old firmware plays instead

With `--protocol 2` (or a belt that has not been reflashed), per-step masks do not
exist. `to_v2_command()` merges each sweep's halves back into one both-motor
pulse, so:

- pulse count survives → **the danger class is still conveyed**
- `left` and `right` survive → **one-sided directions are still conveyed**
- `back` becomes indistinguishable from `front` → **the front/back distinction is lost**

Every downgrade is logged as a warning naming both the intended and the played
direction, so a wearer feeling FRONT for a hazard behind them is explainable from
the log rather than a mystery.

## Deliberate non-goals

- **No direction encoded in rhythm.** Rhythm is spent on the class. Using it for
  both would make the two cues ambiguous.
- **No continuous distance or bearing.** The iOS side reports one of four roles,
  not an angle, so inventing resolution the input does not have would be a lie
  the wearer cannot detect.
- **No repeating alarm.** A pattern is bounded and ends on its own. The iOS
  bridge's own cooldown decides when the next alert may fire; the belt never
  latches on.
