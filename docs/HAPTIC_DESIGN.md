# Haptic design — how information becomes vibration

Everything upstream of the belt produces *information*: which of four directions
a hazard came from, which of three danger classes the AI heard, and how confident
it was. The belt has two vibration motors. This document is the mapping between
the two, and it is implemented in [`laptop/haptic.py`](../laptop/haptic.py).

## The rule, in one sentence

> **Where** you feel it says **where the sound is**.
> **How many times** you feel it says **what the sound was**.
> **How hard** you feel it says **how loud it was**.

The three cues use three separate channels, so they never interfere. "Siren from
the left" and "horn from behind" are unambiguous without the wearer having to
compare them side by side.

## Direction → which motors

| iOS direction | LEFT motor | RIGHT motor | What it feels like |
|---|---|---|---|
| `left` | ■ | | one-sided, left |
| `right` | | ■ | one-sided, right |
| `center` | ■ | ■ *(together)* | symmetric, not to either side |
| `unavailable` | | | nothing is sent |

Those are the three directions iOS stereo reports
(`StereoDirectionEstimator.swift`). **There is no rear cue.** A stereo microphone
pair cannot separate front from back, and the system has no rear sensor, so
inventing a fourth sensation would claim resolution the input does not have.

`unavailable` means iOS's own margin gate was not satisfied, so there is nothing
trustworthy to point at. The belt stays **silent** rather than buzzing vaguely: a
directionless alert teaches the wearer to ignore the belt, which is worse than
missing one event.

Because one mask covers a whole pattern, the wire format needs no per-step motor
switching — see [`../firmware/PROTOCOL.md`](../firmware/PROTOCOL.md).

## Danger class → how many pulses

| Class | Pulses | Pulse length | Gap | Total | Feels like |
|---|---:|---:|---:|---:|---|
| `crash` | 1 | 500 ms | — | 500 ms | one bang |
| `horn` | 2 | 240 ms | 140 ms | 620 ms | beep-beep |
| `siren` | 3 | 260 ms | 150 ms | 1080 ms | wee-oo-wee |

meit-ai's `decision/patterns.py` independently arrived at the same rule — one pulse
for `crash`, two for `horn`, three for `siren` — so this encoding matches what the
AI team designed. Only the timings differ: its `PATTERNS_SHORT` uses 80 ms bursts
to fit a 250 ms gating window that the current iOS-stereo path does not have, and
80 ms is shorter than a coin motor's spin-up. See
[`AI_INTEGRATION.md`](AI_INTEGRATION.md).

Pulse count is the most robust haptic channel available. It survives a loose
belt, a thick jacket, and a wearer who is walking; waveform subtleties do not.
Counting to three is also something a wearer can do without training.

Any other label — `normal` and anything else `meit-ai` reports — produces no
vibration at all.

## Loudness → PWM duty

This follows meit-ai's own rule, in `decision/intensity.py`: confidence decides
*whether* to alert (inside its `judge()`), and **dBFS decides how hard**. A loud
horn a few metres away should feel more urgent than a faint one down the street.

| Measured level | `horn` | `siren` | `crash` |
|---|---:|---:|---:|
| ≤ −40 dBFS | 80 % (37 % duty) | 84 % (38 %) | 88 % (40 %) |
| −30 dBFS | 87 % (40 %) | 89 % (41 %) | 92 % (42 %) |
| −20 dBFS | 93 % (43 %) | 95 % (44 %) | 96 % (44 %) |
| ≥ −10 dBFS | 100 % (46 %) | 100 % (46 %) | 100 % (46 %) |

When no loudness is available — the `/auto/status` route publishes none — the same
bands are driven by confidence between 0.50 and 0.90 instead. Either way a
low-confidence or quiet alert **still fires**: suppressing a real hazard is the
worse error.

### Why the band is so narrow

The floors are high and the ceiling is 46 % duty because of physics, not taste.
The firmware caps duty at 119/255 to keep a 3 V motor at its rated average on a
6.4 V rail, and bench testing on the real belt found **~28 % duty cannot be felt
while ~47 % can**. That leaves roughly 37–46 % as the entire usable range, so every
class's floor sits near the top of it. meit-ai's own 40 %-minimum would land at
~18 % duty and be felt as nothing at all.

Widening the range means changing the motor supply, not the software — see the
electrical note in the README.

`--intensity-scale` multiplies the result at runtime (0.1–2.0) so a demo can be
turned down for a quiet room or up through winter clothing without editing the
profile.

## Constraints the numbers come from

Two hard limits shaped every value above.

**Motor spin-up.** An ERM or coin vibration motor needs roughly 50–80 ms to
reach a perceptible amplitude, so a burst much shorter than that is felt as
*nothing at all* rather than as a short pulse. `MIN_STEP_ON_MS = 100` is enforced
on every emitted step.

**Packet budget.** A packet is a 6-byte header plus 2 bytes per step, and the
pulse count is capped at 4, so the worst case is 14 bytes — inside the 20 payload
bytes an ATT Write Request carries on the default 23-byte MTU. An alert therefore
never depends on MTU negotiation succeeding.

Both limits are checked by `ClassProfile.validate()`, so an edited profile that
violates them fails at load rather than at the demo.

## Tuning it

[`laptop/haptic_profile.json`](../laptop/haptic_profile.json) holds the same
values as the built-in default and can be edited without touching code:

```bash
python -m laptop.haptic_preview --profile laptop/haptic_profile.json
python -m laptop.ios_motor_bridge --profile laptop/haptic_profile.json
```

A unit test asserts the file and the Python default stay identical, so editing
one without the other is caught rather than silently ignored. Constraints
enforced at load:

- `pulses` ≤ 4, so the pattern fits one BLE write
- `on_ms` ≥ 100 ms, so every burst clears the perceptibility floor
- `on_ms` and `gap_ms` multiples of 10 ms, the wire grid
- `1 ≤ min_intensity ≤ max_intensity ≤ 100`

## Deliberate non-goals

- **No direction encoded in rhythm.** Rhythm is spent on the class. Using it for
  both would make the two cues ambiguous.
- **No rear cue.** Stereo cannot separate front from back, so a fourth sensation
  would be a guess the wearer could not detect as wrong.
- **No continuous distance or bearing.** iOS reports one of three directions, not
  an angle, so inventing resolution the input does not have would be a lie the
  wearer cannot detect.
- **No repeating alarm.** A pattern is bounded and ends on its own. The iOS
  bridge's own cooldown decides when the next alert may fire; the belt never
  latches on.
