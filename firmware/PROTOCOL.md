# MEIT EE BLE protocol — CMD v2

```text
iPhone (stereo)  ->  meit-ai  ->  laptop/haptic.py   (decides the pattern)
                                  laptop/belt_client.py  (BLE CMD v2)
                                        |
                                        v
                              ESP32-S3 "MEIT-BELT"
                                        |
                              LEFT / RIGHT vibration motors
```

The ESP32 captures no audio and estimates no direction. It receives a finished
haptic command, validates it, and plays it.

## BLE identity

Unchanged across every firmware revision, so the laptop needs no device-specific
discovery logic:

- Device name: `MEIT-BELT`
- Service UUID: `01000000-1d9e-218f-9a4b-9c4e302a9d11`
- CMD characteristic UUID: `04000000-1d9e-218f-9a4b-9c4e302a9d11`
- Access: write (Write Request, i.e. acknowledged)

## Why one mask is enough

iOS reports `left`, `right`, `center` or `unavailable`, so the belt produces three
sensations: left motor, right motor, or both together. There is no rear cue —
a stereo pair cannot separate front from back, and the system has no rear sensor.

That means **one motor mask applies to the whole pattern**, derived from the
direction byte. No per-step masks are needed, which is what keeps this protocol a
6-byte header instead of 8 and the parser a page of code instead of two.

## Packet

| Byte | Field | Value |
|---:|---|---|
| 0 | magic | `0xA5` |
| 1 | version | `0x02` |
| 2 | sequence | uint8, trace/correlation only |
| 3 | direction | `0` STOP, `1` LEFT, `2` CENTER, `3` RIGHT |
| 4 | intensity | `0..100` percent; `0` only for STOP |
| 5 | step count | `1..4`; `0` only for STOP |
| 6 + 2·i | `on_ms / 10` | `1..255` (10–2550 ms) |
| 7 + 2·i | `off_ms / 10` | `0..255` (0–2550 ms) |

### Size

The longest pattern in use is a siren's three pulses, so the worst case is
`6 + 2 × 3 = 12` bytes, and the hard ceiling at 4 steps is 14. Both are well
inside the 20 payload bytes an ATT Write Request carries on the default 23-byte
MTU, so an alert never depends on MTU negotiation succeeding.

### Example — `siren` from `center`, 98 % duty

```text
a5 02 01 02 62 03 | 1a 0f 1a 0f 1a 00
```

Three 260 ms pulses (`0x1a`) separated by 150 ms gaps (`0x0f`), with no trailing
gap. Reproduce it with `python -m laptop.haptic_preview --bytes`.

## Direction → motors

| Direction | LEFT | RIGHT | Notes |
|---|---|---|---|
| STOP | off | off | also cancels the active pattern and its timer |
| LEFT | on | off | |
| CENTER | on | on | simultaneous |
| RIGHT | off | on | |

## Validation

Implemented in [`main/cmd_parse.c`](main/cmd_parse.c) and rejected before the
motor sequencer sees anything. A malformed packet is refused outright rather than
clamped into something playable — a pattern the wearer cannot interpret is worse
than no vibration, because it teaches them to ignore the belt.

| Rejected | ATT error |
|---|---|
| length below 6, above 14, or ≠ 6 + 2·n | `INVALID_ATTR_VALUE_LEN` |
| magic ≠ `0xA5`, version ≠ `0x02` | `UNLIKELY` |
| direction above 3 | `UNLIKELY` |
| intensity above 100 | `UNLIKELY` |
| step count above 4 | `UNLIKELY` |
| `on_ms = 0` on any step | `UNLIKELY` |
| STOP carrying a pattern or a non-zero intensity | `UNLIKELY` |
| non-STOP with zero steps | `UNLIKELY` |

`cmd_parse.c` is deliberately free of NimBLE dependencies so it compiles and runs
on a host. `firmware/tests/run_cmd_parse_tests.py` builds it with `cc` and checks
it against **golden packets generated by `laptop/protocol.py`**, so the Python
encoder and the C parser cannot silently drift apart:

```bash
python firmware/tests/run_cmd_parse_tests.py
```

## Fail-safe behaviour

- An explicit STOP cancels the running pattern and its timer.
- **BLE disconnect stops the motors** before advertising resumes, so a dropped
  laptop link cannot leave the belt buzzing.
- A pattern is finite and ends on its own; the firmware never latches.
- A new pattern replaces the active one rather than queueing behind it: the most
  recent hazard is the one that matters.

## Laptop-side direction normalization

`laptop/protocol.py::normalize_direction` accepts what iOS reports:

| Input | Result |
|---|---|
| `left`, `right` | `LEFT`, `RIGHT` |
| `center`, `centre` | `CENTER` |
| `front` | `CENTER` — accepted as a spelling of the same thing |
| `back`, `unavailable`, missing, anything else | suppressed — **no packet is sent** |

Suppressing `unavailable` is deliberate: iOS has already decided the direction is
not trustworthy. See [`../docs/HAPTIC_DESIGN.md`](../docs/HAPTIC_DESIGN.md).
